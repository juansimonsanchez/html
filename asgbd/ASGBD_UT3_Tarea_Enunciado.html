Bloque I: Fundamentos Teóricos y Principio del Menor Privilegio (RA3)

    • Un usuario recibe privilegios para crear vistas sobre cualquier tabla de la base de datos liga.
    • Un administrador ejecuta una sentencia de gestión global o altera variables del sistema.

Bloque III: Gestión Avanzada Mediante Roles (RBAC) y Ciclo de Vida (RA3)

Actividad 4: Despliegue de Roles y Activación Automática CE 3.e, 3.g, 3.h

Creación del Rol: Crea un rol administrativo denominado rol_competicion_admin: 
CREATE ROLE IF NOT EXISTS 'rol_competicion_admin';
Dotación de Privilegios al Rol: Concede al rol permisos completos de manipulación (SELECT, INSERT, UPDATE, DELETE) sobre las tablas equipos y partidos de la base de datos liga. Provisión y Enlace: Crea la cuenta 'gestor_liga'@'localhost' identificada con mysql_native_password y vincúlale el rol:

Activación por Defecto: Configura la cuenta para que el rol se active de manera automática en cada inicio de sesión:

Bloque IV: Capa de Abstracción con Vistas y Sinónimos (RA3)

Actividad 6: Diseño de Vistas de Consulta y Ofuscación de Datos CE 3.a, 3.h

Implementa sobre la base de datos liga las siguientes vistas para ocultar información sensible y simplificar consultas analíticas:

  1. v_jugadores_plantilla: Muestra el identificador del jugador, su nombre completo en un único campo (nombre y apellido), su puesto, altura, fecha de alta y el nombre del equipo al que pertenece.
    Requisito de confidencialidad: La columna salario debe quedar estrictamente excluida de la vista. Se deben omitir aquellos jugadores que no tengan equipo asignado.
  2. v_partidos_completos: Lista los encuentros disputados mostrando la fecha, el nombre del equipo local, el resultado formateado como cadena de texto (ej. "82 - 73"), el nombre del equipo visitante y el nombre del árbitro que dirigió el partido.
  3. v_estadisticas_anotadores: A partir de las tablas estadisticas_jugador, jugadores y equipos, muestra para cada jugador su nombre completo, el nombre de su equipo, el total de minutos disputados acumulados, la media de puntos por partido (redondeada a dos decimales) y el total de faltas cometidas.
  4. v_capitanes_equipos: Relaciona de forma unívoca el nombre de cada equipo con el nombre completo de su capitán correspondiente, resolviendo la relación recursiva de la tabla jugadores mediante la clave id_capitan.

Adjunta capturas de la creación de las vistas y de la comprobación ejecutando un SELECT * FROM vista LIMIT 5; sobre cada una de ellas.

Actividad 7: Vistas Actualizables y Cláusula WITH CHECK OPTION CE 3.a, 3.h

Crea la vista actualizable v_pivots_candidatos: 
CREATE OR REPLACE VIEW v_pivots_candidatos AS
SELECT id_jugador, nombre, apellido, puesto, altura, id_equipo
FROM jugadores
WHERE puesto = 'Pívot' AND altura >= 2.00
WITH CHECK OPTION;
Inserta un jugador válido a través de la vista: 
INSERT INTO v_pivots_candidatos (nombre, apellido, puesto, altura, id_equipo)
VALUES ('Pau', 'Gasol', 'Pívot', 2.15, 1);
Aporta captura comprobando que el registro se ha persistido correctamente en la tabla física jugadores. Intenta insertar un registro que incumpla las condiciones de la vista (por ejemplo, con puesto 'Base' o altura 1.92): 
INSERT INTO v_pivots_candidatos (nombre, apellido, puesto, altura, id_equipo)
VALUES ('Ricky', 'Rubio', 'Base', 1.92, 1);
Documenta mediante captura el error de bloqueo (Error 1369) y explica el papel de WITH CHECK OPTION para garantizar la coherencia lógica de los datos.

Actividad 9: Auditoría de Seguridad y Bastionado del Servidor CE 3.c, 3.g, 3.h

En esta actividad final auditarás la seguridad de tu servidor MySQL frente a posibles accesos no autorizados locales y de red. Para cada uno de los aspectos de la lista, debes comprobar en tu entorno si tu instalación es segura o presenta la incidencia.

Uso guiado de la Inteligencia Artificial (IA): Puedes utilizar asistentes de IA (ChatGPT, Gemini, etc.) como apoyo consultivo. Pídele ayuda formulando preguntas claras sobre:

  2. ¿Cómo solucionarlo? Qué sentencia SQL, directiva en my.cnf o cambio de permisos en el sistema operativo corrige el problema si está vulnerable.
Recuerda contrastar críticamente las respuestas de la IA antes de aplicarlas en tu máquina para evitar dejar el servicio inoperativo.

Por cada punto del checklist, debes incluir en la memoria: el resultado de la comprobación .

1. Incidencias Graves (Riesgo Crítico / Compromiso Inmediato)

Fallos que permiten el control total del servidor, ejecución de comandos o acceso remoto no autenticado:

  • Acceso remoto del superusuario root: Comprobar que root solo puede conectar desde localhost (o 127.0.0.1) y jamás desde cualquier IP (%).
  • Usuarios anónimos: Verificar que no existan cuentas con el nombre de usuario en blanco (User = '' en mysql.user).
  • Privilegios globales excesivos: Comprobar que los usuarios de aplicaciones normales no tengan permisos administrativos (SUPER, GRANT OPTION, FILE, SHUTDOWN) ni acceso a *.*.
  • Escritura/Lectura arbitraria de ficheros (secure_file_priv): Comprobar que no esté vacío (""). Debe apuntar a una ruta restringida o estar en NULL.
  • Servicio ejecutado como superusuario del sistema: Verificar que el demonio mysqld se ejecuta bajo el usuario del sistema mysql y nunca como root de Linux.
  • Permisos del directorio de datos (datadir): Comprobar que /var/lib/mysql tiene permisos restrictivos (0700 o 0750) y pertenece a mysql:mysql.

2. Incidencias Moderadas (Superficie de Exposición y Políticas de Acceso)

Debilidades de configuración que facilitan ataques dirigidos, fugas de credenciales o movimientos laterales:

  • Escucha de red innecesaria (bind-address): Si la base de datos solo atiende a aplicaciones en la misma máquina, asegurar que escucha en 127.0.0.1 y no en todas las interfaces (0.0.0.0).
  • Existencia de la base de datos test: Confirmar que se ha eliminado la base de datos test y sus permisos por defecto asociados (test_%).
  • Permisos de los ficheros de configuración: Comprobar que /etc/mysql/my.cnf y sus subdirectorios tienen permisos seguros (0640 o 0600) y son propiedad de root.
  • Cifrado en tránsito (TLS/SSL): Si se permiten conexiones de red, comprobar que require_secure_transport = ON o que se exige SSL a los usuarios remotos.
  • Filtrado por cortafuegos: Asegurar mediante el cortafuegos del sistema (ufw, firewalld o iptables) que el puerto 3306 no está abierto a cualquier origen no autorizado.
  • Historial de comandos con contraseñas: Comprobar que el archivo ~/.mysql_history de los usuarios del sistema no almacena credenciales en texto claro (recomendar vaciado o enlace a /dev/null).
  • Registro general activado (general_log): Verificar que está desactivado (OFF) en entornos reales para evitar guardar contraseñas y datos sensibles en texto claro.

3. Incidencias Leves (Buenas Prácticas y Defensa en Profundidad)

Ajustes recomendados para robustecer la robustez operativa, auditoría y resistencia a ataques de fuerza bruta:

  • Componente de validación de contraseñas: Comprobar si está activo validate_password con directivas mínimas de longitud y complejidad.
  • Política de expiración y bloqueo de cuentas: Verificar si están configurados límites de intentos fallidos (FAILED_LOGIN_ATTEMPTS) y caducidad periódica.
  • Plugin de autenticación seguro: Asegurar el uso de mecanismos modernos (como caching_sha2_password) y evitar plugins desaconsejados u obsoletos.
  • Enlaces simbólicos desactivados: Verificar que la opción symbolic-links = 0 (o skip-symbolic-links) está habilitada.
  • Permisos del registro de errores: Verificar que el archivo indicado en log_error solo puede ser leído por el usuario mysql o administradores (0640).
  • Perfil de confinamiento activo: Comprobar que el servicio cuenta con perfil en modo enforce mediante AppArmor o SELinux.
  • Trazabilidad y auditoría: Identificar la presencia o posibilidad de activar plugins de auditoría para registrar intentos de acceso y cambios de permisos (DCL).
