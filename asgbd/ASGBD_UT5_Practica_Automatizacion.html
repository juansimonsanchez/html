1. DESCRIPCIÓN GENERAL. OBJETIVOS ¶

Trabajas como Administrador de Sistemas y Bases de Datos en una plataforma de comercio electrónico. La base de datos transaccional, llamada ecommerce, almacena un alto volumen de ventas en la tabla ventas_temporales. Para evitar que esta tabla ralentice el sistema de producción, la dirección técnica ha establecido las siguientes directrices:

  1. Consolidación Interna (MySQL): Cada noche a las 03:00 AM, un evento interno del SGBD debe mover todas las ventas completadas del día anterior a una tabla histórica consolidada llamada historico_ventas. Los registros consolidados deben ser eliminados de la tabla activa de producción de forma transaccional. Toda ejecución del evento debe quedar auditada en una tabla de log interna (registro_logs).

  2. Copia de Seguridad Externa y Rotación (Bash + Cron): Cada madrugada a las 04:00 AM, un script de sistema en Bash debe realizar una copia de seguridad lógica, consistente e InnoDB-safe de la base de datos ecommerce. El script debe comprimir el volcado, añadirle una marca de tiempo y almacenarlo en /backup/ecommerce/. Además, para optimizar el almacenamiento del servidor, el script debe purgar automáticamente cualquier copia de seguridad con más de 7 días de antigüedad.

  3. Plan de Recuperación (DRP): Se debe simular un fallo total del esquema y verificar el proceso de restauración lógica garantizando la integridad de los datos.

3. ACTIVIDADES A REALIZAR ¶

Fase 1: Creación de la Infraestructura en MySQL ¶

Crea la base de datos ecommerce y define las siguientes tablas con el motor InnoDB:

  • ventas_temporales: Contiene id_venta (Autonumérico), cliente (VARCHAR), monto (DECIMAL 10,2), fecha_venta (DATETIME) y estado (VARCHAR: 'Pendiente', 'Completado').

  • historico_ventas: Estructura idéntica a la anterior más un campo fecha_consolidacion (TIMESTAMP).

  • registro_logs: Tabla de auditoría interna con id_log (Autonumérico), nombre_evento (VARCHAR), mensaje (TEXT) y fecha_registro (TIMESTAMP).

Puebla la tabla ventas_temporales con al menos 5 registros de prueba, asegurando que algunos tengan estado 'Completado' y otros 'Pendiente'.

Fase 2: Programación del Evento de Mantenimiento (ev_consolidar_ventas) ¶

  1. Verifica que el planificador de eventos de MySQL está configurado de forma persistente y activo.

  2. Crea el evento ev_consolidar_ventas para ejecutarse diariamente a las 03:00 AM (puedes ajustar el tiempo a EVERY 1 MINUTE de forma temporal para las capturas de demostración).

  3. Requisito de Robustez: La consolidación debe realizarse bajo transacciones seguras (START TRANSACTION, COMMIT, ROLLBACK). Si el traspaso de registros a historico_ventas tiene éxito, se eliminan de ventas_temporales y se guarda un registro en registro_logs. Si falla, se hace rollback y se audita el error.

Fase 3: Script de Automatización de Backups en Bash (backup_sistema.sh) ¶

Desarrolla un script en /usr/local/bin/backup_sistema.sh que cumpla con los siguientes estándares profesionales de administración de sistemas:

  1. Crear el directorio /backup/ecommerce/ si no existe.

  2. Definir variables para credenciales de MySQL (usando un archivo de configuración de accesos seguro o variables cifradas de entorno de forma recomendada).

  3. Utilizar mysqldump con el parámetro --single-transaction para no bloquear lecturas/escrituras.

  4. Redirigir el archivo .sql resultante, comprimirlo al vuelo usando gzip para ahorrar espacio, y nombrarlo con el patrón: backup_ecommerce_YYYYMMDD_HHMMSS.sql.gz.

  5. Mecanismo de Rotación Práctica: Buscar y eliminar de manera automática todos los ficheros .gz del directorio /backup/ecommerce/ que tengan una fecha de modificación superior a 7 días.

  6. Guardar la salida y posibles errores del script en un fichero de log del sistema /var/log/backup_ecommerce.log.

Fase 4: Integración en el Planificador de Tareas de Linux (Cron) ¶

Configura el planificador de Linux (crontab de root) para programar la ejecución del script anterior cada madrugada de forma automática a las 04:00 AM.

Fase 5: Simulación de Desastre y Verificación de la Integridad ¶

  1. Simula una catástrofe de datos haciendo un DROP DATABASE
ecommerce;.

  2. Procede a restaurar la base de datos a partir del último archivo comprimido .gz disponible.

  3. Verifica la consistencia: comprueba que las tablas se han recuperado de forma íntegra, con sus restricciones de clave y que el log de eventos contiene el historial de consolidación.
