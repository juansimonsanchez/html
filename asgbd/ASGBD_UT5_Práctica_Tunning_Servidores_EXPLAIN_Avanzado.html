1. DESCRIPCIÓN GENERAL. OBJETIVOS ¶

En un entorno de producción real, el rendimiento de las bases de datos no se limita de forma única al diseño de índices individuales. A menudo, un mal tuning de las variables internas del motor de almacenamiento de bases de datos (InnoDB en este caso) o la ausencia de monitorización avanzada mediante esquemas del sistema (sys y performance_schema) provocan graves retrasos de servicio.

En esta práctica, el alumno asumirá el rol de un Administrador de Sistemas de Bases de Datos (DBA) que se enfrenta a un servidor MySQL saturado por la ineficiencia. Sus objetivos principales son:

  1. Analizar y ajustar parámetros críticos del motor en caliente y frío a través del archivo de configuración general (mysqld.cnf).

  2. Monitorizar accesos e identificar cuellos de botella reales mediante la base de datos de rendimiento sys.

  3. Auditar, refactorizar y reestructurar consultas multitabla complejas con alto coste de CPU/RAM utilizando la traza avanzada del planificador EXPLAIN.

2. CONSIDERACIONES PREVIAS ¶

  • Se utilizará la instancia virtual Linux del alumno sobre infraestructura OpenStack (o similar).

  • Se trabajará con la base de datos de pruebas corporativa jardineria ampliada con un generador masivo de registros para asegurar un volumen de almacenamiento realista en tablas medianas.

  • La interacción con la instancia de MySQL se realizará exclusivamente a través de sesión SSH interactiva utilizando clientes nativos.

3. ACTIVIDADES A REALIZAR ¶

Fase 1: Tunning de Variables del Motor InnoDB y Configuración del Servidor ¶

El alumno debe auditar el estado de los recursos físicos del host que están asignados al SGBD.

  1. Consulta de Estado Inicial: Ejecute los comandos de inspección en consola de MySQL para consultar los valores establecidos de forma predeterminada para las variables del motor:

    • max_connections (Límite máximo de sesiones concurrentes de red).

    • innodb_buffer_pool_size (La asignación de memoria RAM para caché de páginas de datos e índices InnoDB).

    • innodb_log_file_size (Tamaño máximo reservado para el archivo del Redo Log de transacciones en disco).

  2. Ajuste Físico en Frío: Modifique el archivo de configuración general del servicio (habitualmente /etc/mysql/mysql.conf.d/mysqld.cnf) utilizando privilegios de administrador de sistemas para establecer los siguientes valores orientados a un host de producción de 4 GB de RAM:
    [mysqld]
    max_connections = 150
    innodb_buffer_pool_size = 1536M
    innodb_log_file_size = 256M
    innodb_flush_log_at_trx_commit = 2

  3. Reinicio y Verificación: Reinicie el servicio de
forma limpia utilizando el gestor del sistema (systemctl restart mysql).
Verifique en los ficheros de log de errores del sistema
(/var/log/mysql/error.log) que la asignación física de memoria buffer se
ha inicializado correctamente. Capture la salida y verifique de forma
interactiva en la consola con SHOW VARIABLES que los nuevos valores
están cargados en caliente.

Fase 2: Diagnóstico de Sentencias Lentas y Consultas más Ejecutadas ¶

Antes de tocar el esquema, el DBA debe saber exactamente qué consultas están lastrando el rendimiento del host.

  1. Activación de los Trazados de Rendimiento: Asegúrese de que el esquema performance_schema está habilitado.

  2. Uso de la Base de Datos SYS: Acceda a la base de datos de administración simplificada sys de MySQL.

  3. Identificación de Sentencias Ineficientes: Ejecute una consulta de auditoría técnica sobre la vista statements_with_temp_tables u statements_with_sorting para listar las consultas que están provocando la creación de tablas temporales en memoria o disco o que tienen altos costes de ordenación secuencial.

  4. Consulta de Mayor Ejecución: Extraiga las 5 estructuras de sentencias agrupadas que consumen un mayor porcentaje de tiempo acumulado de CPU en el SGBD utilizando la tabla events_statements_summary_by_digest de performance_schema, visualizando las columnas DIGEST_TEXT y COUNT_STAR.

Fase 3: Optimización Estructural de Consultas Multitabla Complejas ¶

Se ha reportado una caída de rendimiento masiva en la plataforma web al consultar el siguiente reporte histórico de facturación de agentes de ventas:

SELECT
e.nombre AS agente,
e.puesto,
c.nombre_cliente AS cliente,
p.codigo_pedido,
p.fecha_pedido,
SUM(dp.cantidad * dp.precio_unidad) AS subtotal_pedido
FROM empleado e
LEFT JOIN cliente c ON e.codigo_empleado = c.codigo_empleado_rep_ventas
LEFT JOIN pedido p ON c.codigo_cliente = p.codigo_cliente
LEFT JOIN detalle_pedido dp ON p.codigo_pedido = dp.codigo_pedido
WHERE c.pais = 'USA' AND dp.cantidad > 20
GROUP BY e.codigo_empleado, c.codigo_cliente, p.codigo_pedido
ORDER BY subtotal_pedido DESC;

  1. Auditoría con EXPLAIN (Antes de Optimizar): Ejecute el diagnóstico del plan de ejecución sobre la consulta multitabla anterior. Documente de forma técnica y exhaustiva los valores de:

    • La columna type en cada uno de los pasos de las tablas unidas (JOIN).

    • El número estimado de filas procesadas (rows) y su producto cartesiano resultante.

    • Los avisos de la columna Extra (por ejemplo, busque la existencia de Using temporary o Using filesort).

  2. Identificación de Cuellos de Botella: Identifique
razonadamente qué relaciones JOIN o filtrados WHERE están obligando al
motor a procesar de forma secuencial completa las tablas.

  3. Estrategia de Optimización (DDL): Diseñe e implemente las estructuras físicas de optimización necesarias:

    • Considere la implementación de índices compuestos estratégicos para las claves foráneas que unifican las relaciones multitabla, ordenándolas adecuadamente según el prefijo izquierdo.

    • Establezca un índice compuesto que permita cubrir tanto la restricción de país como el enlazado del código del cliente.

  4. Auditoría con EXPLAIN (Después de Optimizar): Vuelva a ejecutar el diagnóstico de la traza sobre la consulta original. Compare en un cuadro estructurado:

    • La reducción en el número total de estimaciones de accesos físicos (rows).

    • Los cambios en el método de acceso de cada paso (ALL a ref o range).

    • La remoción o permanencia de costosas tablas temporales internas en el servidor.
